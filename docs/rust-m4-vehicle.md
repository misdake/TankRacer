# M4 vehicle rendering

## M4.1 accepted (2026-11-17)

The Rust browser now draws the authored body, turret and gun instead of the box.
This increment changes render extraction and submission only. Game/physics source,
fixed updates, input rules, RNG, spawn and camera behavior are unchanged.

### Resource and state ownership

- `scene::vehicle::VehicleScene` reads the existing `VehicleModel` and `pose::State`.
  Each part has local geometry, a material atlas, a world transform and a geometry
  revision. It never receives mutable gameplay state.
- Local model vertices are in world units (/128); published part translations
  are in physics units (/1024). The boundary reflects Z once. Part poses already
  contain authored offsets, body lean, turret yaw and gun pitch/recoil; the renderer
  does not reapply those operations or compose them under a second body transform.
- Current private geometry is authoritative, including body/turret collision
  damage, hidden faces and gun-vertex recoil. A small exact geometry comparison
  detects changes without modifying simulation owners or introducing hash collisions.
  Only changed parts are prepared/uploaded. Pose-only updates use model uniforms.
- One vehicle atlas reuses the existing clamped, padded, premultiplied texture
  policy. Opaque, masked, double-sided and blended faces use the existing explicit
  material states. Blended parts join the same triangle order as world/scenery;
  opaque vehicle parts write depth before all blended geometry.
- `web::vehicle_view` owns GPU resources. Atlas pixels are released after upload;
  CPU geometry/cache metadata and GPU resources have normal session ownership.
  Vehicle render caches are reported separately from extra per-map preprocessing.

## M4.2 accepted (2026-11-17)

Both authored track meshes now render from `poses.tracks`, including independent
suspension pitch and translation. The wheels are textured faces inside those
meshes, not separate rotating wheel models. Their animation follows the original
eight wheel-atlas rows and five tread phases, using the model's qualified UV
triangle/corner tables. No additional geometry is invented.

### Animation and GPU design

`scene::vehicle::tracks::Tracks` owns two wrapping visual travel counters.
After each successful fixed simulation update the browser adapter samples the
existing track speed, yaw rate and handbrake lock without writing gameplay state.
The original 434B70 arithmetic clamps speed to +/-300000, truncates yaw*400/1024,
and accumulates left/right speed minus/plus turn. High-speed overflow, unsigned
counter wrap and reverse travel retain the x86 behavior. Handbrake locks the
counters; pausing updates stops visual progression too. New sessions reset them.

Original 434C60 maps `(travel >> 17) & 7` to wheel rows 32 apart, and
`(travel >> 17) % 5` to tread offsets two rows apart. The original helper was
called by drawing; Rust advances visual travel at fixed updates so rendering
frequency, skipped draws and repeated camera-only redraws cannot alter it.
The old C presenter's capped latest-speed estimate for skipped frames is not
used. This is presentation state and consumes no RNG.

At load time, preparation emits phase-zero UVs and optional per-corner scroll
coefficients. Only animated mesh passes allocate the extra attribute-9 stream;
ordinary world/scenery vertices keep their existing 44-byte layout. Each part
draw supplies two phase uniforms. The vertex shader wraps V to the source byte
range inside the atlas region before interpolation, including the 250+8 -> 2
tread boundary. Uniforms are explicit on every draw and ordinary VAOs disable
the optional stream. Existing alpha/cull/depth states remain authoritative.

Animation changes neither vertex/index buffers nor geometry revisions. Normal
damage/recoil preparation still uploads only a changed part. A changed animated
prototype also refreshes its scroll stream; session resource teardown releases it.

## M4.3a accepted: shadows and normal attachments (2026-11-17)

The normal Under/End parts now use their authored meshes/materials and existing
attachment poses. The Bottom mesh is deliberately not added to the exterior:
it belongs to the original third camera's dedicated cockpit presentation.

Ground projection reads `motion.hull`, which already holds the qualified
42DFE0 output: four contacts ordered 1/3/2/0, quantized local vertices and an
identity-basis world position. The renderer preserves the original shadow mesh
indices and RGB32/alpha128 straight-alpha appearance. It hides the uninitialized
projection until the first completed contact update, rather than drawing it at
the world origin. A changed projection uploads only four vertices (176 B);
camera-only redraws upload nothing. No ground query or gameplay calculation is
duplicated for drawing.

The modern renderer uses explicit LEQUAL depth testing, no depth writes and
polygon offset [-1,-1] for this coplanar ground decal. Base scenery renders first,
then the ground projection, then the vehicle, then depth-sorted transparent
geometry. The actual pixel test caught 50 coplanar vehicle-underbody pixels
receiving the decal when it was submitted after the vehicle. Moving the vehicle
after the decal fixes that contamination; no physics or projection vertices were
changed to conceal the error.

Whole-vehicle shade comes directly from the existing primary-contact
`special_count`, using the original signed-byte >1 gate. The fragment shader
halves expanded diffuse RGB bytes with truncation before texture modulation
(neutral white 255 -> 127), preserving alpha. Every body/track/attachment draw
sets this state explicitly; scenery and the ground shadow do not inherit it.

## M4.3b accepted: chase cameras and cockpit (2026-11-17)

The driving scene now uses typed original 4057F0 camera calculations instead
of the floating-point proxy follow camera. C cycles near/far/cockpit on a rising
edge; V holds look-back; F retains free inspection. All six authored camera
parameter groups are read from OBPARAMS, including cockpit drag and the near/far
displacements. The Q12 basis, roll, signed angle wrapping, smoothing and /8
published-position quantization survive the render boundary.

The fixed-update order is explicit: read the pre-update Player pose, advance
the camera, publish its position/forward to the existing world update, update
the Player, then copy turret-local feedback for the *following* camera tick.
Drawing never advances the camera or publishes feedback. Existing physics
formulas are untouched; the external camera inputs deliberately change from
the previous proxy to the original integer values. The native probe's `--chase`
option uses the same order, and `--views` adds a short cycle/look-back sequence.

Mode 2 uses the original Bottom mesh at `bottom_position` with `poses.reference`;
ordinary body/turret/tracks/attachments and the ground projection are hidden.
The mesh receives the same whole-car shade, while XHAIR.SUR remains neutral.
The sight center uses the original turret pose and `5120 + 4*min(recoil,0)`
offset. Its original descriptor (531BA8, checked in the executable) is 300x300
with pixel UVs [0,0,63,63]. Sprite UVs therefore use source pixels in the atlas,
not mesh-byte /256 normalization. The quad follows camera right/up, including
roll. Explicit premultiplied blend, LEQUAL, no depth write and two-sided state
come from the actual alpha surface class; it is drawn after world transparency.
The cockpit mesh uses ordinary material/depth passes. Old painter sort biases
are not converted into arbitrary physical displacements in this 3D renderer.
